# tests

Plain Node scripts, no framework and no install. Run one directly:

```bash
node tests/free-sessions.test.js
node tests/pull-from-day.test.js
```

Each exits non-zero if anything fails, so they work in a pre-push hook or CI
unchanged.

These are here because the logic they cover is the kind you cannot check by
looking at the screen: it is either arithmetic about money or a copy that
silently shares state. The functions are duplicated from `app.js` rather than
imported, because `app.js` is one big IIFE with no exports — so **if you change
the original, change the copy here too, or the test is guarding nothing.**

| _(ported)_ `package-price.test.js` | `bankPackagePrice` — what a month of a membership costs a given athlete | Ported to `src/money/pricing.spec.js` (Phase 3 extraction): the module is imported for real now, assertions carried verbatim, plus pins for the branches its drifted copies missed (the program-only rate guard, flatRate precedence). It used to be sized by counting bookings on the first app open of the month, so a 12-session athlete with three sessions on the calendar was billed $255 against a $1,020 membership, and athletes with an empty calendar got no ticket at all. Covers: the ticket is the membership, over/under booking never moves the price, the advisory count, and manual grants staying untouched. |
| `free-sessions.test.js` | birthday + referral grants, and what a free session is worth | Both passes run on every calendar load, so a missing idempotency guard hands out a session per page load — it doesn't throw and doesn't look wrong, the balance just climbs. Covers: fires once per year / once per referred person however often the pass runs, never before the day, lands late if the app wasn't opened, no back-granting a birthday typed months later, Feb 29, self-referral, deleted referrer — plus the ledger proof that a free package never expires, is spent only after the paid allowance, and never appears in what's owed. |
| `nutrition-import.test.js` | the nutrition-tracker importer's pure half — CSV parse, file sniffing, column resolution, row mapping, and deriving a food library from a diary | It eats a file the app does not control. `IMPORT_SOURCES.cron` was read from a real Cronometer export, and the test asserts against the vendored copy of that export, so a renamed vendor column fails the suite instead of failing an athlete's import silently. The behaviours pinned here are the ones that break quietly: `0.00` is a real logged value while an empty cell is unknown (fold them together and every rollup misreports the day), two byte-identical rows are two separate servings, a logged recipe is one row and not its ingredients, `Amount` carries a multi-word unit, and gram foods must normalise to `per100` from the *most recent* portion — an older row gives a number close enough to look right and wrong for every portion logged afterwards. |
| _(ported)_ `repeat-from-session.test.js` | `repeatStarts` — which sessions "Make this a regular session" creates | Ported to `src/scheduling/series.spec.js` (Phase 4 extraction): the module is imported for real now, assertions carried verbatim, plus the primitives (dowOfISO/nextDowISO/weeklyOccurrences/patternOccurrences) and dowsPhrase get direct pins. Original rationale: The coach reaches it from a session that has usually already happened, and `patternOccurrences` starts from the first matching weekday *on or after* the date it is handed — so the tapped date would quietly re-book the past. Nothing errors; last Tuesday just reappears on the calendar. Covers: a past session starting in the future, a session earlier today rolling a week while one later today is kept, several weekdays staying in step, clock time surviving a DST change, and the count the button promises equalling the rows written. That last one is why "for how long" is a horizon and not a session count: the first occurrence can drop, so 3 weeks can legitimately mean 2 sessions, and the button has to say 2. |
| `workout-clock.test.js` | `WorkoutClock` — how long a session is recorded as lasting | The summary said "24 minutes" after a 72-minute workout and nothing on screen said which was right. Three under-counts at once: gaps over the 5-min idle cap were discarded whole instead of credited up to it, `onVisible` re-stamped the clock so every screen-lock-during-rest vanished, and `enter()` zeroed the session so a trip to another tab restarted it. Covers: the cap credits rather than drops, no cliff at 5:00, screen-off rest counts, a long absence stays bounded, same-day re-entry continues and a different day starts fresh, and the per-commit 3-hour cap. |
| _(ported)_ `blocked-time.test.js` | `availability.blocks` — the time a coach has closed off, and what it subtracts | Ported (with `cancel-window.test.js`) to `src/scheduling/availability.spec.js` (Phase 4 extraction): the real `normalizeAvailability`/`generateSlots`/`blackoutsMirrorOf` are imported now instead of trimmed copies, and a wiring layer pins that `saveCoachAvailability` rebuilds the mirror through the module. Original rationale: It is the only rule that removes a slot from BOTH sides at once, since the coach's quick-picks and the athlete's grid are one `generateSlots` call: get it wrong and you either hand out a session the coach isn't there for or silently delete a working afternoon, and neither throws. The boundaries earn most of it — a block starting exactly when a slot ends must leave that slot alone, and half an hour out of the middle still costs the whole hour. The other half is the `blackouts` mirror: it used to be the only way to say "day off" and is now derived from the all-day blocks purely for athletes on a cached PWA, so a wrong derivation is invisible on this build and wrong on theirs. Adoption of legacy days off has to be idempotent because a cloud refresh hands the old array back on every pull. |
| `muscle-coverage.test.js` | `musclesForExercise` / coverage — turning an athlete's week into sets per muscle group | Nothing on screen tells you the body map is lying; it just lights up confidently wrong. Both bugs it pins were found by running the finished feature on a real program. The three exercise→muscle sources have to UNION rather than short-circuit: "Deadlift" appears in the curated list only under Lower Back, because that list means "a good example of that muscle", not "all this exercise trains" — treating it as authoritative reported a week of squats, deadlifts and RDLs as **zero glute work**. But the union then has to be held back in one place: the demo database files every shoulder movement under a single "shoulders" tag, and letting that coarse bucket fan out across all three delt heads overwrote the curated lists — the only source that knows a lateral raise from a face pull — so front, side and rear delts all printed the **same number**. The two fixes pull against each other, which is exactly why they need pinning together. Also covers secondary work counting half, the library category staying a floor rather than an override, and an unrecognised lift being counted as unmapped instead of silently credited to something.
| `training-level-plumbing.test.js` | that `trainingLevel` reaches all four places it has to | The field is set by the coach and read by the athlete's own copy of the coverage map, so it has to survive `makeClient` → `athleteToRow` → `rowToAthlete` → `buildProgramFromAthlete`. That last one is a hand-picked allowlist rather than a spread, so a new field is simply absent unless somebody remembers — and the failure is silent: the coach's map is right, the athlete's quietly uses default bands, and neither screen says they disagree. |
| `anatomy-coverage-wiring.test.js` | whose record the athlete's coverage map reads | `state.clientData` is a wrapper — `{program, progress}` — and an athlete's weeks live one level down at `program.client.weeks`. The map shipped reading the wrapper, so `coverageWeek()` got `undefined`, bailed, and every athlete who opened Coverage got "add a week with some days": coach copy, on their phone, about a program that plainly exists. Nothing threw and nothing looked broken. A source-text grep for the literal `state.clientData.weeks` cannot catch a regression here — the bug was `coverageSubject()` aliasing `client` straight to `state.clientData`, a parameter alias rather than a dotted chain a regex could see — proven when a reviewer reverted it and the full suite still passed. The real pin uses `fnBody()` (the same brace-matcher `training-level-plumbing.test.js` uses) to pull `coverageSubject()` and `athleteCoverageClient()` out of the live `app.js` and execute them; reverting the fix makes that check fail for real, verified by hand both ways. Also pins that the fix makes `client === null` newly reachable for an athlete with no program at all — which left the coach's "No athlete open" label reachable one line above the correctly athlete-voiced note beneath it, until that got the same `isCoach` branch. |
| `band-tags.test.js` | the five band colors, and their absence from lift identity | The band is the load, not the implement. A barbell squat really is a different lift from a dumbbell squat, which is what `LIFT_ID_GROUPS` is for; a green band is not a different lift from a grey one, any more than 225 is a different lift from 315. Adding `"Band"` to `LIFT_ID_GROUPS` would shatter every athlete's banded history into five unrelated short chains with nothing climbing between them — silently, and only visible months later as a graph that never goes anywhere. Most of this file exists to fail loudly if that happens. Also pins the tag order (which *is* the ladder — nothing else stores it), single-select, one group per color, and that no two bands share a hex, since here the color is the information. |
| `day-icon-tokens.test.js` | that every `workoutIconFor()` result reaches a renderer | `workoutIconFor()` used to return an emoji, so printing it raw worked everywhere. When it started returning keys into `DAY_ICON_SVGS` instead (`"sd:claw"`), the athlete-side call sites were converted to `dayIconHtml()`/`setDayIcon()` in the same commit and two coach-side ones were not — the Day Library grid and the "Import a day into &lt;week&gt;" picker printed the literal text `sd:claw` in place of an icon for four weeks. Nothing threw: a token is a perfectly good string, so the failure renders as a tidy box with `sd:claw` typed in it. Pinning the two fixed lines would only guard the two bugs already found, so this sweeps **every** call site in `app.js` and requires each to be wrapped, stored rather than rendered, or bound to a local that the same function later hands to a renderer. Also pins the invariant that makes the raw form wrong in the first place: every branch of `workoutIconFor()` returns an SVG token, never printable text. |
| `move-program-day.test.js` | `moveProgramDay` — the ⇄ Move day splice | A filled day's history rides on identity: logs, completions and moods are keyed by day/exercise ids, so the move must splice the SAME object — a clone with a fresh id orphans every log silently while the program looks right. Also pins the same-week off-by-one: positions are labelled as the user sees them pre-removal, so a forward move that spliced at the raw index would land one slot past where they tapped. Plus: cross-week append, an emptied week left standing, and no-op guards that touch nothing. |
| `day-card-tap-targets.test.js` | that the middle of a day card still opens the day | "Skipped it?" and "⇄ Move" were inline spans in `.workout-card-meta` with `padding: 0.55em 0.35em; margin: -0.55em 0 …` under `@media (pointer: coarse)`. Both halves of that misfire: vertical margin is ignored on an inline element so it cancelled nothing, and vertical padding does not lay out but DOES hit-test — so a 27px invisible target hung across the meta line, which on a ~100px two-line card is the card's own centre. On a tablet, tapping a day opened the skip sheet or the day mover instead, and cancelling out landed back on the day list, so it read as "the day won't open" with nothing on screen explaining why. Measured in Chromium at eight tablet/phone geometries: up to 43% of a 44px fingertip at the card's centre. Desktop never saw it — a mouse pointer means the coarse block is inert, which is also why every harness passed. Pins the markup (controls in `.wc-actions`, a sibling of the body, never in the meta line) and the CSS (no negative vertical margin, `inline-flex` so padding takes real space, `.wc-actions` a column not a row — a row under the meta is still mid-card and measured as no fix at all). |
| `skip-day.test.js` | the whole-day skip's engine rulings and the 15% pullback | Three rulings that fail invisibly if wrong. A `deload:true` entry must be judged like a skip — judged as an attempt, the lighter bar reads "under target = miss" and the ladder STALLS for taking the offer the app itself made; judged as a hit, reps climb off a weight that was never the target. The pullback math floors to the ladder's grain and deliberately goes below the written weight (the automatic backoff's floor there would deliver "15% lighter = 0%" to exactly the athlete sitting at the floor) but never below one grain. And the streak counter: a partially-logged date is a real occurrence — one logged lift means they showed up — so it breaks the run rather than extending it. |

Tests for domains that have been extracted out of the IIFE do not live here:
they move to `src/**/*.spec.js` in the same commit as the code, where they
`import` the shipped module for real instead of brace-matching it out of
`app.js`. So far: Phase 1 (sync) moved `merge-exercise-logs.test.js`,
`template-tombstones.test.js`, `roster-progress.test.js` and
`sync/program-allowlist.spec.js` to `src/sync/merge-logs.spec.js`,
`src/sync/merge-by-id.spec.js`, `src/sync/roster-progress.spec.js` and
`src/sync/program.spec.js`; Phase 2 (training) moved
`tags/pause-and-equipment.spec.js` to `src/training/tags.spec.js` and
`skip-day.test.js` to `src/training/progression.spec.js`. Header stories
and assertions intact throughout.
